## 1. 结论摘要

用户反馈全部有事实依据。系统现在“能跑”，但存在明显的语义压缩、输入渠道不足、数据覆盖不足和解释力不足：

1. “不接受高强度加班”会被模型泛化为“不接受加班”，而总结又隐藏工作强度字段。
2. 图片没有 OCR；DOCX 没有解析；扫描 PDF 没有 OCR；上传原文件实际上没有保存。
3. 岗位 URL 明确没有抓取器，因此无法打开链接。
4. 背调当前是 `jd_only` 模板化安全降级，不是联网背调。
5. 稀疏画像下 20 个岗位全部 49 分；固定中性分制造了虚假的精确百分比。
6. 当前数据库只有 20 条有效岗位，其中存在重复岗位，难以验证推荐质量。

## 2. 复测证据

### 2.1 画像语义失真

精确输入：

```text
我不接受高强度加班
```

实际抽取：

```json
{
  "overtime_tolerance": "不接受",
  "labor_intensity": "排斥高强度"
}
```

实际总结只展示：

```text
加班接受度：不接受
```

根因：

- `backend/app/agents/profile_agent.py` 的 LLM 枚举把“加班频率”和“劳动强度”分别抽取，但没有“限定范围不可泛化”规则。
- `_extract_rule_based_updates()` 能识别 `labor_intensity=排斥高强度`，却无法阻止 LLM 同时写入更宽泛的 `overtime_tolerance=不接受`。
- `_build_completion_message()` 展示 `overtime_tolerance`，不展示 `labor_intensity`，导致限定条件消失。
- LLM 偶尔返回字符串 `"null"`；现有代码只过滤真正的 JSON `null`，字符串可能进入画像。
- `frontend/src/views/ProfileView.vue` 的加班下拉框只有“不接受/偶尔/接受”，无法表达“偶尔正常加班可以，但拒绝长期高强度”。

对照输入：

```text
我不接受高强度加班，但偶尔正常加班可以接受
```

运行结果为 `overtime_tolerance=偶尔`、`labor_intensity=排斥高强度`，说明系统有两个字段，但缺少可靠的语义约束和联合展示。

### 2.2 图片与简历上传

| 输入 | 实测 | 结论 |
|---|---|---|
| PNG 图片 | HTTP 400，“无法从文件中提取有效文本” | 没有图片 OCR |
| TXT 简历 | HTTP 200；本科、学校、1 项目、3 技能 | 文本输入主链可用 |
| PDF | 代码只尝试 PyPDF2 文本层 | 扫描 PDF 必然失败；依赖也未固定在 requirements |
| DOCX | 前端不允许，后端无 python-docx | 未实现 |

代码证据：

- `frontend/src/views/ProfileView.vue` 只接受 `.pdf,.txt,.md`。
- `backend/app/api/profile.py` 对 PDF 只调用文本提取；导入 `pdf2image` 后没有执行 OCR。
- `backend/requirements.txt` 没有固定 `PyPDF2/pdf2image/python-docx/pytesseract` 等解析依赖。
- `file_path=f"uploads/{user_id}/{filename}"` 只是数据库字符串，代码没有实际写入原文件。
- `profile_agent.parse_resume()` 完全依赖一次 LLM JSON 输出；没有 JSON 修复、分段解析和人工确认。

### 2.3 岗位 URL

输入任意纯 URL 后，接口返回 code=1：当前未接入可核验岗位网页抓取能力，要求粘贴完整 JD。

根因位于 `backend/app/agents/job_parser.py`：URL 输入被主动拒绝。这是此前为了避免“没抓网页却让模型猜内容”设置的正确安全边界，但产品能力尚未补上。

### 2.4 背调内容过少且没有联网证据

对一份正常 JD 实测：

| 指标 | 结果 |
|---|---:|
| `verification_status` | `jd_only` |
| 外部来源 | 0 |
| 总结长度 | 71 字 |
| 建议长度 | 42 字 |
| 完整报告 | 172 字 |
| 社保/劳动争议/工商/口碑 | 全部未核验 |

`backend/app/agents/background_check.py::_real_web_search()` 固定返回“未接入可核验联网数据源”。因此当前页面不是联网搜索失败，而是根本没有联网供应商或官方来源适配器。

### 2.5 推荐全部同分/原因重复

新用户稀疏画像实测：数据库 20 个岗位全部为 49 分。

固定分来自：

```text
方向缺失 12 + 城市缺失 10 + 薪资缺失 10 + 技能/要求缺失 17 = 49
```

较完整测试画像（完整度 48）分布：

```text
62 分 × 2
42 分 × 1
37 分 × 1
27 分 × 1
17 分 × 15
```

重复解释：

- 20/20 都提示城市不匹配。
- 20/20 都提示技能或要求数据不足并取中性分。
- 17/20 方向不匹配。
- 只有 3 个岗位命中方向，3 个岗位命中薪资。

根因位于 `backend/app/services/job_service.py::_score_job()`：缺失信息直接加固定中性分；评分没有单独的“证据覆盖率/置信度”；硬约束不做过滤；技能为空仍展示精确百分比。

### 2.6 岗位数量与质量

- 当前有效岗位：20 条。
- 薪资缺失：1 条。
- 存在 2 条相同“示例科技有限公司 / Java 后端开发工程师”。
- 数据量过小，且缺少持续更新、过期下架、去重和来源质量等级。

## 3. 二阶段产品模型

### 3.1 画像不再只存粗枚举

加班画像拆为：

```json
{
  "overtime_frequency": "偶尔",
  "overtime_intensity_limit": "拒绝高强度/长期",
  "acceptable_conditions": ["上线紧急情况", "有调休或加班费"],
  "hard_constraints": ["拒绝长期高强度加班"],
  "raw_evidence": "我不接受高强度加班，但偶尔正常加班可以接受",
  "confidence": 0.98
}
```

抽取必须返回原文证据；较宽泛字段不能覆盖更具体限定。每次重要更新先回复：

```text
我的理解是：你可以接受偶尔、短期的正常加班，但不接受长期或高强度加班。这个理解正确吗？
```

用户确认后再作为硬约束用于推荐。

### 3.2 上传与解析流水线

建议实现：

```text
MIME/大小校验
  → 原文件安全保存 + SHA-256
  → PDF/DOCX/图片/TXT 分类解析
  → 文本层提取
  → 无文本时 OCR
  → 确定性章节切分
  → LLM 结构化抽取 + JSON Schema 校验/修复
  → 用户预览确认
  → MySQL/Chroma 入库
```

支持范围：PDF、DOCX、TXT、MD、PNG、JPG、JPEG、WEBP。图片和扫描 PDF 使用本地 PaddleOCR 或 Tesseract；优先本地处理，减少简历个人信息外发。

错误必须区分：格式不支持、文件损坏、没有文本层、OCR 失败、LLM JSON 失败、数据库失败、向量库失败。

### 3.3 安全岗位 URL 抓取

实现两级抓取：

1. `httpx + BeautifulSoup/正文抽取` 处理服务端渲染页面。
2. 合规允许且确有需要时用 Playwright 处理 JavaScript 页面。

必须包含 SSRF 防护：只允许 HTTP/HTTPS；阻止 localhost、内网、保留地址和 DNS 重绑定；限制跳转、响应体、超时和内容类型；记录最终 URL、标题、抓取时间和正文证据片段。

站点需要登录、验证码或条款禁止自动化时停止抓取，提示用户粘贴 JD 或上传截图，不绕过限制。

### 3.4 背调证据对象

每条结论必须落为：

```json
{
  "provider": "来源名称",
  "source_url": "可打开链接",
  "fetched_at": "抓取时间",
  "published_at": "原始发布时间/年度",
  "field": "工商状态/行政处罚/被执行信息/年报社保人数",
  "excerpt": "支撑结论的原文片段",
  "source_hash": "内容哈希",
  "confidence": "verified/partial/conflicting"
}
```

注意：法院裁判文书数量不等于劳动仲裁数量；年报社保人数也不等于当前实时员工人数，必须标明年度和企业自报属性。

### 3.5 推荐评分重构

不再对未知项加固定中性分。分开计算：

- `fit_score`：只对有证据维度归一化。
- `coverage`：当前可评估信息覆盖率。
- `hard_constraint_status`：通过/冲突/未知。
- `reason_evidence`：画像原文与 JD 原文字段对照。

当 coverage 低于阈值时显示“画像不足，暂不评分”，不能显示 49% 之类的伪精确数字。

推荐顺序：硬约束过滤 → 方向/技能/经历匹配 → 软偏好 → 数据可信度 → 结果多样性。每个岗位至少给出独有命中项和最大缺口；相同模板原因合并为顶部说明，不在每张卡重复。

## 4. 合规岗位数据与背调来源

### 4.1 推荐的岗位数据顺序

1. 政府开放数据/API。
2. 企业官网招聘页和公开 ATS 页面，遵守 robots 与服务条款。
3. 用户主动提交的岗位 URL/截图。
4. 商业招聘平台只在有正式 API、数据授权或合作协议时接入。

北京市公共数据开放平台的“单位招聘岗位信息”是现实可用的首个种子源：页面显示由市人社局提供、无条件开放、约 20,220 条、每 15 天更新，并给出 API 调用方式：  
https://data.beijing.gov.cn/zyml/ajg/srlsbj/466e22a6b0314b4298864dcfb1a50803.htm

抓取入库必须做来源标记、字段映射、公司/岗位指纹去重、过期下架和增量更新。

1. 企查查或天眼查正式开放 API：工商、经营风险、法律风险等；需要采购和用途合规审核。

3. 中国执行信息公开网等司法公开查询只展示可直接核验的个案证据。
4. 员工口碑只能作为“未经独立核验的个体陈述”，逐条引用，不能汇总成确定事实。

商业 API：

- 企查查开放平台：https://openapi.qcc.com/services/aboutUs
- 天眼查开放平台：https://open.tianyancha.com/api_list

官方核验：

- 国家企业信用信息公示系统：https://www.gsxt.gov.cn/

## 5. 实施顺序

### P0-A：画像语义保真

- 新增细粒度加班/强度约束与原文证据。
- 过滤 `"null"/"unknown"/空字符串`。
- 规则与 LLM 冲突时保留更具体语义并要求用户确认。
- 总结联合展示频率、强度、条件和硬约束。

验收：至少 30 条同义、否定、转折、纠正用例；“不接受高强度加班”不得总结为“不接受任何加班”。

### P0-B：简历与图片可靠上传

- 原文件真实保存、哈希和所有权。
- PDF/DOCX/图片解析与 OCR。
- 分阶段中文错误；解析预览确认后再入库。

验收：文本 PDF、扫描 PDF、DOCX、PNG/JPG、TXT/MD 各有成功样本；损坏、空白、超大、伪扩展名均明确失败且不污染画像。

### P0-C：推荐去伪精确

- `fit_score + coverage + hard_constraints`。
- 稀疏画像不显示百分比。
- 技能、城市、薪资、强度、单双休给出字段级证据。
- 岗位去重与过期管理。

验收：空画像不再所有岗位同分；改变城市/加班硬约束产生可预测过滤；相同岗位不重复。

### P1-A：URL/截图解析

- 安全抓取器、正文抽取、动态页受控回退、截图 OCR。
- 输出原文证据和抓取元数据。

验收：允许访问的静态页/动态页成功；内网 URL、超大响应、跳转环、验证码站点安全失败；绝不由模型补写未抓到的 JD。

### P1-B：岗位数据扩充

- 先接政府开放岗位数据。
- 再接允许抓取的企业招聘页。
- 定时增量、去重、过期、质量评分。

验收：至少 500 条近期、来源可追溯岗位；重复率低于 2%；过期岗位可自动下架。

### P1-C：证据化企业背调

- 先选择一个商业 API 供应商，或仅做官方查询链接与人工核验工作流。
- 建立证据表和冲突/过期处理。
- 报告按“已核验/部分核验/未核验”输出，不给统一模板结论。
