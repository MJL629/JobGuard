# JobGuard 大模型实验报告

日期：2026-08-25  
模型：Qwen2.5-7B-Instruct  
硬件：AutoDL vGPU-32GB（RTX 4080 SUPER）

## 1. Agent Trace 与评估

实现了基于 JSONL 的轻量 Trace，使用 `trace_id / request_id / span_id` 关联请求、Agent 节点和 LLM 调用，记录状态、异常、Token 与耗时。

JobParser 端到端基线：

- 3 条真实请求，零错误
- JSON 合法率、必填字段完整率、字段值准确率均为 100%
- Prompt Token 1602，Completion Token 719
- Agent 平均耗时 5437ms，P95 5860ms

评测同时发现并修复了本地 vLLM `max_model_len=3000` 与 Agent 默认 `max_tokens=4096` 的冲突。

## 2. vLLM Serving 实验

默认配置并发从 1 提升至 16 时：

| 并发 | RPS | 输出 Token/s | TTFT P50 | E2E P95 |
|---:|---:|---:|---:|---:|
| 1 | 0.75 | 44.69 | 47ms | 1.43s |
| 4 | 2.89 | 164.47 | 47ms | 1.44s |
| 8 | 5.55 | 309.17 | 58ms | 1.59s |
| 16 | 9.53 | 553.42 | 65ms | 1.90s |

KV Cache 对照：

- `gpu_memory_utilization=0.70, max_model_len=2048`：显存约 21.7GB，理论并发 57.85
- `gpu_memory_utilization=0.90, max_model_len=6000`：显存约 28.1GB，理论并发 39.31
- 对当前短 Prompt，两档并发 16 吞吐均约 9.7 RPS，差异很小

Batch 调度对照：

- 将 `max_num_seqs` 限制为 8 后，并发 16 吞吐从约 9.5 降至 5.2 RPS
- TTFT P50 从约 65ms 上升至 1436ms
- 结论：对当前业务不应把 `max_num_seqs` 设置得过低

补充参数矩阵（RTX 4090，Qwen2.5-7B，BF16，并发 16，每组 32 请求）：

|---:|---:|:---:|---:|---:|---:|---:|---:|---:|
| 4096 | 0.90 | 开 | 20,900MB | 12.28 | 718.46 | 68.62ms | 18.94ms | 100% |
| 8192 | 0.90 | 开 | 20,844MB | 11.43 | 668.93 | 58.73ms | 19.20ms | 100% |
| 16384 | 0.90 | 开 | 20,116MB | 12.32 | 721.09 | 57.59ms | 19.06ms | 100% |
| 8192 | 0.80 | 开 | 18,436MB | 12.58 | 743.97 | 63.17ms | 19.05ms | 100% |
| 8192 | 0.95 | 开 | 22,076MB | 12.64 | 742.61 | 64.20ms | 19.02ms | 100% |
| 8192 | 0.90 | 关 | 20,844MB | 12.29 | 726.40 | 52.62ms | 19.10ms | 100% |

这组短 Prompt 负载中，各档吞吐差异约在噪声范围内；`0.95` 相比 `0.80` 多占约 3.6GB 显存，却没有形成稳定的吞吐优势。Prefix Cache 开启也未改善短 Prompt 的 TTFT，说明它更适合长且高度重复的系统前缀。生产默认建议采用 `max_model_len=8192`、`gpu_memory_utilization=0.80`，按业务需要开启 Prefix Cache；需要 16K 上下文时再切换到 16384。

## 3. LoRA SFT

构造数据：120 Train / 20 Val / 20 Test。所有实验训练 20 个优化步骤，目标模块为 `q_proj/v_proj`。

| LoRA r | 可训练参数 | Train Loss | Val Loss | 字段准确率 | 精确匹配率 | 峰值显存 |
|---:|---:|---:|---:|---:|---:|---:|
| 4 | 1,261,568 | 0.2122 | 0.1653 | 83.85% | 0% | 16.28GB |
| 8 | 2,523,136 | 0.1221 | 0.0741 | 86.15% | 0% | 16.30GB |
| 16 | 5,046,272 | 0.0382 | 0.0096 | 98.46% | 80% | 16.33GB |

结论：在当前数据规模下选择 `r=16`，质量提升明显，额外显存成本很小。

## 4. DPO

Preference 数据：80 Train / 20 Test。以 SFT r16 为 Policy，以禁用 Adapter 的 Base 模型为 Reference。

首轮 DPO 发生过优化：偏好 Margin 提升到 2.51，但字段准确率降至 31.54%。保留该失败实验作为对照后，将学习率降至 `1e-5`、步数降至 4。

保守 DPO 结果：

- Base / SFT / DPO Preference Win Rate 均为 100%（当前测试集饱和）
- 平均偏好 Margin：0.389 → 0.523 → 0.598
- JSON 合法率 100%
- 字段准确率 93.85%，精确匹配率 50%

结论：DPO 增强偏好置信度，但相对 SFT r16 仍有约 4.6 个百分点的任务质量回退。当前生产候选应使用 SFT r16，后续需要增加更困难且更真实的 Preference 数据。

## 5. 产物

Agent 系统优化补充：

- 增加任务复杂度模型路由：短结构化任务优先本地 vLLM，复杂推理任务路由到推理模型，并记录路由原因
- 增加 `prompt_version`、精确匹配 TTL Cache 与命中事件
- 所有 LLM 调用在发送前执行上下文字符预算裁剪，保留 System 与最近消息
- 企业信息/口碑检索和批量岗位匹配改为真实异步并行，并限制并发
- Agent 节点 Trace 增加脱敏后的输入/输出摘要与输出状态
