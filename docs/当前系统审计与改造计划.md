## 7. 重点问题分析

### 7.1 首次进入后 AI 不会主动建立画像

`ChatView` 的 `onMounted` 只创建会话并更新连接状态，没有请求欢迎消息或缺失字段，见 `frontend/src/views/ChatView.vue:112-122`；只有用户点“快速开始”才发送固定文本，见第 326-329 行。后端创建会话也只插入 `ChatSession` 后返回，见 `backend/app/api/chat.py:43-58`。

应让创建会话返回 onboarding 状态，或新增 onboarding start 接口：后端读取当前用户画像、计算缺失项、持久化第一条助手消息并返回第一条中文问题。

### 7.2 多轮对话是否真正提取并保存画像

后端存在真实路径：`build_profile` 会调用 `extract_updates`，再由 `update_profile` 提交 MySQL，见 `backend/app/api/chat.py:181-217`、`backend/app/services/profile_service.py:70-139`。但不能判定为完整完成：

- 抽取器只收到当前一条用户消息，没有最近多轮历史：`api/chat.py:181-185`。
- `existing_info` 传入但没有放入抽取 Prompt：`agents/profile_agent.py:238-274`。
- 前端忽略 `profile_updated.updated_fields`：`ChatView.vue:203-221`。
- 刷新页面不加载聊天历史，`messages` 总从空数组开始：`ChatView.vue:107-122`。
- LLM 输出不是严格 JSON 时会静默得到空更新；Mock 回复必然无法作为画像 JSON。

结论：**后端具备逐轮抽取和持久化代码，但多轮上下文、用户确认、历史恢复和端到端验证未完成。**

### 7.3 画像是否持久化 MySQL

是。模型、commit 和查询链路存在，且 `/api/profile/1` 实测读到完整度 52、6 个项目、28 个技能、1 条教育经历。证据：`backend/app/models/user.py:34-126`、`backend/app/services/profile_service.py:70-223`。

但完整度持久值可能错误：`update_profile` 使用 `_profile_to_dict(profile,{})` 算分，而该字典没有偏好、项目和技能，见 `profile_service.py:129-132,404-419`。因此数据库分数可能与聊天中合并偏好后的实时分数不一致。

### 7.4 推荐为什么未按画像生成；数据库岗位是否显示

- 岗位页从未调用列表/推荐 API，直接使用固定 `jobs`：`JobListView.vue:100-141`。
- REST `/api/jobs/recommend` 明确是占位：`backend/app/api/jobs.py:40-51`。
- 聊天推荐读取真实画像和岗位，但声明匹配前 15 条后调用 `match_batch(..., top_k=5)`；匹配器内部只取 `jobs[:top_k]`，实际仅评估前 5 条：`api/chat.py:373-386`、`agents/job_matcher.py:111-147`。
- 模型失败时所有岗位统一返回 50 分和 `Unable to evaluate`，仍可能被展示：`job_matcher.py:99-109`。

结论：数据库确有 17 条岗位，但前端没有显示；当前岗位页推荐分全部是前端固定值。

### 7.5 岗位分析页与后端解析

岗位分析页没有导入 `analyzeJob`，`startAnalysis` 仅运行固定定时器并写固定报告，见 `JobAnalysisView.vue:97-174`，所以没有真实调用后端。

后端 `JobParser` 注释宣称 WebFetch/OCR，但实现只把原字符串送给 LLM；URL 没有抓取、截图没有 OCR，`input_type` 只参与标记，见 `backend/app/agents/job_parser.py:1-8,90-150`。

### 7.6 企业背调、来源引用与大模型虚构风险

没有真实联网和可核验引用。`_real_web_search` 没调用搜索引擎、HTTP 抓取或企业数据 API，而是让 LLM“提供你所了解的信息”，见 `backend/app/agents/background_check.py:25-47`。返回结构没有 sources、URL、发布时间、抓取时间、原文片段或证据等级，见第 297-310 行。

虚构风险很高：

- Prompt 在无证据时仍要求尽量给具体人数、日期、金额：`background_check.py:31-46`。
- 风险评估要求社保人数、劳动争议数和口碑判断：`background_check.py:151-208`。
- 模型输出的社保/仲裁数字会尝试直接写企业表：`backend/app/services/job_service.py:181-214`。
- 前端固定展示社保 45 人、仲裁 2 起：`JobAnalysisView.vue:155-171`。

该能力不能称为“真实 WebSearch”。无证据必须返回“未核验”，禁止补具体数字；每个结论须绑定来源 URL、抓取时间、原文证据与置信度。

### 7.7 简历是否真实定向生成；上传是否保存解析

前端简历页不是，固定生成 Zhang San 演示简历：`ResumeView.vue:108-160`。

后端代码层面会读取画像和目标岗位，检索/选择项目、改写、自评、组装和生成招呼语：`backend/app/services/resume_service.py:53-90`、`backend/app/agents/resume_generator.py:259-318`。但项目改写 Prompt 强制要求量化结果和 JD 关键词，即使原项目没依据，见 `resume_generator.py:118-151`。`fact_check_resume` 与 `safeguard_resume` 虽已定义，却未进入主 `generate` 链路；事实核查异常时还返回 `has_fabrications=False`，属于失败开放，见第 673-766 行。

上传分入口：

- 画像页上传只打印文件名：`ProfileView.vue:221-223`。
- 聊天页会调用 `/api/profile/1/upload-resume`：`ChatView.vue:246-273`。
- 后端会解析文本，将原始文本和结构化字段写 MySQL，并尝试同步 Chroma：`api/profile.py:43-109`、`profile_service.py:31-66,247-402`。
- 原文件没有实际保存；仅把 `uploads/{user_id}/{filename}` 字符串写进数据库：`api/profile.py:88-92`。
- DOC/DOCX 没有专用解析，会被当 UTF-8 容错解码；`PyPDF2/pdf2image` 当前本机已安装但没有列入 `requirements.txt`，新环境不可复现。

### 7.8 英文与固定数据原因

`ProfileView.vue`、`JobListView.vue`、`JobAnalysisView.vue`、`ResumeView.vue` 仍是早期原型，标签和对象直接写在组件内，未接 `src/api`。这不是国际化方案，也不是数据库数据。

### 7.9 固定 user_id=1 的影响

- 所有访客创建 user 1 的会话并向其上传画像，造成串号、覆盖和隐私泄漏。
- 请求方可自行传任意 user_id 读写他人画像、分析或简历，形成 IDOR 越权。
- 登录 Token 与业务身份脱节；即使登录，业务仍操作 user 1。
- 多用户并发共享画像与推荐基础，结果失真且无法审计。

证据：`ChatView.vue:115,251`；`backend/app/api/profile.py:31-145`、`jobs.py:40-83`、`resume.py:24-72`、`chat.py:43-83` 均未使用当前用户依赖。只有 `auth.py:133-149` 的 `/me` 使用 `get_current_user_id`。

### 7.10 LangGraph 重复构图、空节点和未调用节点

是：

1. `backend/app/graph/builder.py:136-228` 构建并在导入时全局编译一套图；业务节点仅改状态，是空实现，见第 40-85 行。
2. `backend/app/agents/graph.py:202-297` 又构建一套图；画像节点只改内存不写 DB，JobMatcher 节点为空；直接走 resume 分支时没有先产生 job_info。
3. 正式聊天接口 `backend/app/api/chat.py:63-142` 使用手写 if/elif，没有调用任一图。
4. `route_by_intent` 被聊天 API 导入后未使用：`api/chat.py:20`。
5. 图测试只验证存在和可编译，空节点也能通过：`backend/tests/test_graph.py:11-39`。

结论：生产请求没有真正使用宣称的 LangGraph 多智能体编排。

### 7.11 SSE 丢失、重复和截断风险

- 前端每次用最新 `data.content` **覆盖** `assistantContent`，不追加：`ChatView.vue:175-180`。后端简历流程发送两条 message，完整简历会被后续下载提示覆盖：`api/chat.py:353-366`。
- 只在流结束后 push 最后一段，不是真正 token 流式：`ChatView.vue:188-195`。
- 结束时不处理剩余 buffer，也没对 decoder 收尾，末尾不完整行/多字节可能丢失：`ChatView.vue:156-186`。
- 只接受 `data: ` 单行 JSON；不支持无空格或多行 data。
- JSON 错误被静默跳过：`ChatView.vue:181-183`。
- event 类型被丢弃，`error` 的 message 不显示：`ChatView.vue:169-183,203-221`。
- 无 event_id、sequence、去重、重连与幂等，重放可能重复。
- 请求硬编码 `http://localhost:8000`，绕过 Vite 代理：`frontend/src/api/chat.js:13-23`。

## 9. 产品完整业务链路

1. 注册/登录：JWT 决定当前用户，服务端不接受客户端指定他人 ID。
2. 首次引导：自动创建 onboarding 会话，根据画像缺失项主动首问。
3. 简历导入：原文件受控保存，记录哈希/类型/大小；可靠解析 PDF/DOCX/TXT；用户确认解析结果。
4. 画像完善：简历和多轮对话增量写 MySQL；返回旧值/新值/完整度；画像页可查看纠错。
5. 岗位入库展示：保存来源 URL、抓取时间和原文；岗位页读取 MySQL 并做后端筛选分页。
6. 画像推荐：硬条件预筛 + 技能/项目排序；展示每项得分依据与数据缺口。
7. 岗位分析：抓取真实 JD；企业事实绑定来源、时间、摘录、置信度；无证据显示未核验。
8. 定向简历：只使用确认过的经历和目标岗位，禁止新增无依据技能、经历与数字。
9. 事实校验确认：强制规则核验，用户逐项确认后保存版本和 PDF。
10. 历史反馈：持久化会话、画像变更、分析、简历版本和反馈，可追溯来源。

## 10. 分阶段改造顺序与验收标准

### 阶段 0：停止假成功，建立安全边界

改造：标识/禁用 Mock；移除 user_id=1；业务接口统一 JWT 与所有权校验；登录接通；清洗 Markdown；无来源背调禁止具体事实。

改造：登录注册/刷新/退出接 Pinia；自动画像首问；恢复历史；画像页真实读写；抽取使用多轮历史；修复完整度。

验收：文件可找回且哈希一致；三类文件成功/失败用例明确；新增岗位刷新可见；筛选分页正确；history/search 不再 422。

### 阶段 3：可解释推荐

改造：实现 REST 推荐；确定性硬过滤 + 技能/经历评分；聊天和页面共用服务；失败时明确规则降级。

### 阶段 4：有证据的岗位分析

改造：URL 抓取/OCR；合规企业数据源；证据对象；前端展示来源、时间、摘录、不确定性与失败。

验收：解析字段可定位原文；每项事实有 URL/来源/时间/摘录；断网/无数据绝不生成具体数字；同证据集可复现。

### 阶段 5：可信定向简历

改造：简历页接真实岗位/历史/结果；主链强制 fact-check 与 safeguard；数字必须有原始依据；版本化 PDF。

验收：不同岗位选择不同真实项目且可解释；学校/技能/项目/日期/数字均可回指；诱导虚构必须被阻断；历史和 PDF 可用。

### 阶段 6：收敛 LangGraph、SSE 与质量体系

改造：保留一套生产图并让 API 调用；定义 event_id/type/sequence/delta/done/error；实现累加、尾缓冲、去重、重连、历史对账；CI 加 unit/API/E2E；健康检查分 liveness/readiness。

验收：trace 证明请求经过真实节点；SSE 随机分块、中文拆分、断线重放后无丢失/重复/截断；核心 E2E 全绿。
