### 2.2 最终方案：三模型分工

| 用途 | 模型 | 服务商 | Base URL | 免费额度 | 理由 |
|------|------|--------|----------|----------|------|
| **主力（对话/解析/生成）** | GLM-4-Flash | 智谱AI | `https://open.bigmodel.cn/api/paas/v4` | 永久免费 | 128K 上下文，中文能力强，OpenAI 兼容，社区案例丰富 |
| **企业背调（强推理）** | DeepSeek V3 (`deepseek-chat`) | DeepSeek 官方 | `https://api.deepseek.com/v1` | 新用户 100万 token | 完整版 V3 推理链条深，多维度分析判断能力强，比赛项目够用 |
| **Embedding** | BGE-M3 | SiliconFlow | `https://api.siliconflow.cn/v1` | 永久免费 | 中文 Embedding 效果好，OpenAI 兼容 |

> **为什么企业背调用 DeepSeek V3 而不是蒸馏版？**
> DeepSeek V3 官方 API 是完整版模型，推理能力远超 8B 蒸馏版。企业背调需要同时分析社保人数、劳动争议、网络口碑、JD 话术等多个维度并综合判断，对推理深度要求高。100 万 token 对比赛项目完全够用。

### 3.2 Agent 详细设计

#### Agent 1：用户画像 Agent

| 属性 | 内容 |
|------|------|
| **触发条件** | 用户首次使用、主动说"更新我的信息"、对话中发现画像信息不完整 |
| **输入** | 用户上传的简历文件 + 对话文本 |
| **核心能力** | 1. 解析简历提取结构化字段（姓名、学历、技能、项目经历）<br>2. 通过对话追问缺失信息（期望薪资、工作地点、强度偏好等）<br>3. 将所有信息结构化存入 MySQL + 向量化存入 Chroma |
| **输出** | 完整的用户画像 JSON + 存入用户知识库 |
| **使用的 LLM** | GLM-4-Flash（对话）+ GLM-4.7-Flash（长简历解析） |

**Prompt 设计要点**：
- 对话式收集，每次只问 1-2 个问题，不一次性轰炸
- 追问逻辑：先收集硬性条件（薪资/地点/岗位方向），再收集软性偏好（强度/文化）
- 项目经历要求用户描述：项目名称、角色、技术栈、量化成果

#### Agent 2：岗位解析 Agent

| 属性 | 内容 |
|------|------|
| **触发条件** | 用户粘贴岗位链接、上传岗位截图、从岗位库选择岗位 |
| **输入** | URL / 截图 / 岗位文本 |
| **核心能力** | 1. URL 解析：通过 WebFetch 获取页面内容，提取结构化岗位信息<br>2. 截图解析：OCR + LLM 提取岗位信息<br>3. 输出统一的岗位结构化数据 |
| **输出** | 结构化岗位 JSON（公司名、岗位名、薪资范围、地点、JD 详情、技术要求） |
| **使用的 LLM** | GLM-4-Flash |

**提取字段**：

#### Agent 4：岗位匹配 Agent

| 属性 | 内容 |
|------|------|
| **触发条件** | 用户请求推荐岗位 / 企业背调完成后 |
| **输入** | 用户画像 + 岗位信息（单个或列表） |
| **核心能力** | 1. 从用户知识库检索用户技能、项目、偏好<br>2. 从岗位库检索匹配岗位<br>3. 计算多维度匹配度分数<br>4. 排序输出推荐列表 |
| **输出** | 匹配度评分 + 推荐理由 |
| **使用的 LLM** | GLM-4-Flash |

**匹配度计算维度**：
| 维度 | 权重 | 说明 |
|------|------|------|
| 技能匹配 | 40% | JD 技术要求与用户技能的匹配程度 |
| 经验匹配 | 20% | 项目经历与岗位职责的关联度 |
| 薪资匹配 | 15% | 岗位薪资是否在用户期望范围内 |
| 地点匹配 | 10% | 工作地点是否符合用户偏好 |
| 强度匹配 | 15% | 工作制度（单双休/加班）是否符合用户接受度 |

#### Agent 5：简历生成 Agent（含招呼语）

| 属性 | 内容 |
|------|------|
| **触发条件** | 用户确认投递某岗位 |
| **输入** | 用户画像 + 目标岗位信息 |
| **核心能力** | 1. 从用户知识库检索所有项目经历<br>2. 根据 JD 筛选最相关项目（RAG 检索）<br>3. 按含金量排序<br>4. 针对岗位方向改写项目描述<br>5. 注入匹配技能关键词<br>6. 生成自我评价段落<br>7. 组装完整简历<br>8. 生成招呼语 |
| **输出** | 完整简历（可导出 PDF）+ 招呼语文本 |
| **使用的 LLM** | Qwen2.5-7B 或 GLM-4-Flash |

**简历生成流程**：
```
1. RAG 检索：用户知识库中检索与 JD 关键词相关的项目经历 → 返回 top-5
2. 项目筛选：LLM 从 top-5 中选出最匹配的 2-3 个
3. 排序：按项目复杂度、成果量化程度、与岗位关联度排序
4. 改写：每个项目根据岗位方向调整侧重点
   - 后端岗 → 强调系统设计、高并发、数据库优化
   - 算法岗 → 强调模型效果、数据处理、评估指标
   - 前端岗 → 强调用户体验、性能优化、组件设计
5. 关键词注入：自然融入 JD 中的技能关键词
6. 自我评价生成：结合用户背景和岗位要求，生成 2-3 句个人总结
7. 招呼语生成：简短投递附言，突出匹配亮点
```

#### Agent 6：调度与自检 Agent（Orchestrator）

| 属性 | 内容 |
|------|------|
| **触发条件** | 贯穿全局，每次 Agent 调用前后 |
| **核心能力** | 1. 意图识别：判断用户意图，路由到对应流程<br>2. 状态管理：维护整个会话的状态（当前阶段、已完成步骤）<br>3. 冲突仲裁：多 Agent 输出冲突时裁决（如知识库与实时检索冲突）<br>4. 结果审查：检查各 Agent 输出质量和一致性<br>5. 错误处理：Agent 调用失败时的降级和重试策略 |
| **使用的 LLM** | GLM-4-Flash（轻量判断） |

### 3.3 LangGraph 状态定义

```python
from typing import TypedDict, List, Optional, Annotated
from langgraph.graph.message import add_messages

class JobGuardState(TypedDict):
    """JobGuard 全局状态"""
    
    # 会话信息
    messages: Annotated[list, add_messages]  # 对话历史
    user_id: str                             # 用户 ID
    session_id: str                          # 会话 ID
    
    # 意图路由
    intent: str                              # "build_profile" | "analyze_job" | "generate_resume" | "recommend_jobs"
    current_stage: str                       # 当前阶段
    
    # 用户画像
    user_profile: Optional[dict]             # 用户完整画像
    user_projects: Optional[list]            # 用户所有项目经历
    
    # 岗位信息

## 四、RAG 知识库设计

### 4.1 三个知识库详设

#### 知识库 1：用户知识库（user_kb）

| 属性 | 内容 |
|------|------|
| **Collection 名** | `user_{user_id}_kb` |
| **存储内容** | 用户简历信息、所有项目经历、技能、教育背景、偏好（薪资/地点/强度） |
| **分块策略** | 按项目/经历分段，每段 300-500 字 |
| **Embedding 模型** | BGE-M3 (SiliconFlow) |
| **检索方式** | 按用户 ID 隔离 + 语义检索 |
| **元数据** | `{type: "project"|"skill"|"education"|"preference", title: str, tech_stack: list}` |

**检索场景**：
- 简历生成时：`检索：与"Java后端开发"相关的用户项目经历` → 返回 top-5 项目
- 岗位匹配时：`检索：用户掌握的所有技能` → 返回技能列表
- 偏好查询：`检索：用户的工作地点和薪资期望` → 返回偏好

#### 知识库 2：企业/岗位知识库（company_kb）

| 属性 | 内容 |
|------|------|
| **Collection 名** | `company_job_kb` |
| **存储内容** | 历史分析过的企业信息、岗位信息、风险评估结果 |
| **分块策略** | 按企业分段，每家企业一个 chunk（含多次分析记录） |
| **Embedding 模型** | BGE-M3 |
| **检索方式** | 语义检索 + 企业名精确匹配 |
| **元数据** | `{company_name: str, job_title: str, analyzed_at: datetime, risk_level: str}` |

**数据优先级规则**：
```
用户上传的岗位信息  >  实时 WebSearch 检索结果  >  知识库历史数据

冲突时：以优先级高的为准，但保留低优先级数据作为参考
```

#### 知识库 3：简历范例知识库（resume_kb）

| 属性 | 内容 |
|------|------|
| **Collection 名** | `resume_examples_kb` |
| **存储内容** | 按岗位类型分类的优质简历范例、项目描述改写模式、技能关键词库 |
| **分块策略** | 按岗位类型 + 项目类型分段 |
| **Embedding 模型** | BGE-M3 |
| **检索方式** | 按岗位类型检索相似范例 |
| **元数据** | `{job_category: str, project_type: str, quality_score: int}` |

### 4.2 RAG 检索策略

```
┌──────────────────────────────────────────────────────┐
│                   RAG 检索流程                         │
├──────────────────────────────────────────────────────┤
│                                                      │
│  1. 查询预处理                                       │
│     ├─ 提取关键词（技术栈、岗位名、公司名）            │
│     └─ 生成检索 query                                │
│                                                      │
│  2. 多路检索                                         │
│     ├─ 向量检索（语义相似度）→ top_k=10              │
│     ├─ 关键词检索（精确匹配）→ 补充结果               │
│     └─ 元数据过滤（user_id、job_category）            │
│                                                      │
│  3. 结果融合与重排序                                  │
│     ├─ 去重                                          │
│     ├─ 按相关度 + 时效性加权排序                      │
│     └─ 返回 top_k=5                                  │
│                                                      │
│  4. 上下文注入                                        │
│     └─ 将检索结果注入 Agent 的 prompt                │
│                                                      │
└──────────────────────────────────────────────────────┘
```

    session_type    VARCHAR(50)  NOT NULL COMMENT '会话类型：profile_building/job_analysis/resume_generation/general',
    status          VARCHAR(20)  DEFAULT 'active' COMMENT '状态：active/completed/archived',
    context_json    JSON         COMMENT '会话上下文（LangGraph状态快照）',
    created_at      DATETIME     DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
    INDEX idx_user_session (user_id, session_type, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='对话会话表';
```

#### 表 12：chat_messages（对话消息表）

```sql
CREATE TABLE chat_messages (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    session_id      BIGINT       NOT NULL COMMENT '会话ID',
    role            VARCHAR(20)  NOT NULL COMMENT '角色：user/assistant/system',
    content         MEDIUMTEXT   NOT NULL COMMENT '消息内容',
    message_type    VARCHAR(50)  DEFAULT 'text' COMMENT '消息类型：text/job_link/image/resume_card',
    metadata_json   JSON         COMMENT '附加元数据',
    created_at      DATETIME     DEFAULT CURRENT_TIMESTAMP,
    
    FOREIGN KEY (session_id) REFERENCES chat_sessions(id) ON DELETE CASCADE,
    INDEX idx_session (session_id),
    INDEX idx_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='对话消息表';
```

### 5.3 数据优先级在数据库层的体现

当发生数据冲突时，通过以下字段判断优先级：

```sql
-- 岗位信息来源优先级
-- source_type 字段取值：
--   'user_input'      → 优先级最高（用户直接提供）
--   'websearch'       → 优先级中等（实时检索）
--   'knowledge_base'  → 优先级最低（历史数据）

-- 示例查询：获取某岗位最新且最可靠的信息
SELECT * FROM jobs 
WHERE company_name = 'XX科技' AND job_title = 'Java后端'
ORDER BY 
    FIELD(source_type, 'user_input', 'websearch', 'knowledge_base'),
    created_at DESC
LIMIT 1;
```

## 八、关键技术决策记录

| 决策 | 结论 | 原因 |
|------|------|------|
| LLM 主模型 | GLM-4-Flash（智谱AI） | 永久免费、128K上下文、OpenAI兼容、社区案例丰富 |
| LLM 推理模型 | DeepSeek V3 官方（deepseek-chat） | 完整版模型推理能力强，100万token比赛够用 |
| Embedding | BGE-M3（SiliconFlow） | 免费、中文效果好、OpenAI兼容 |
| 前端框架 | Vite + Vue 3 + Element Plus | 现代标准方案、评委认可度高 |
| 多智能体框架 | LangGraph | 有状态编排、条件路由、人机交互 |
| 向量数据库 | Chroma | 轻量级、Python原生、零部署 |
| 关系数据库 | MySQL 8.0 | 结构化数据标准方案 |
| 前后端通信 | REST API + SSE 流式 | 对话场景需要流式输出 |
| 岗位数据获取 | 用户粘贴 + LLM WebSearch 实时检索 + 种子数据导入 | 免维护、真实数据 |
| API Key 管理 | .env 环境变量 | 安全、标准做法 |
