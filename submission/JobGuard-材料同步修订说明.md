# JobGuard 提交材料同步修订说明

> 来源：结合桌面早期材料、当前项目代码、现有 docs 审计记录与最新提交材料母版整理。  
> 目的：指出早期材料哪些内容可保留、哪些必须同步，避免答辩时被问到“功能是否真实完成”。

## 1. 可以保留的内容

早期材料中以下方向仍然正确，可以继续使用：

- 项目定位：AI 驱动的求职避雷与简历优化 Agent。
- 核心痛点：求职信息不透明、岗位真假难辨、简历不匹配、企业风险难核验。
- 主业务链路：画像构建 -> 简历解析 -> 岗位推荐 -> 岗位分析 -> 定向简历。
- 技术主线：Vue 3 + FastAPI + MySQL + LangGraph + ChromaDB。
- 创新表达：证据门禁、画像/岗位/简历联动、Agent 工作流。
- 视频结构：登录、画像、简历、推荐、分析、定向简历、总结。

## 3. PPT 需要替换的页

### Slide 4 技术架构

增加：

- MCP Python SDK
- AgentRun / ToolTrace / Evaluation
- Alembic
- JWT 认证
- OCR / DOCX / PDF 解析

删除或弱化：

- “Prometheus 完整监控”
- “BM25 已全面覆盖所有检索场景”如果无法在演示中证明，可放到后续优化。

### Slide 7 岗位推荐与避雷分析

不要写“61 个岗位全量背调”作为当前结论。建议改成：

- 岗位库包含种子岗位与北京市公共数据开放平台导入记录。
- 推荐展示匹配分、证据覆盖率、硬条件冲突和需要确认项。
- 企业核验区分官方来源、已联网查询、受访问控制、未核验。

### Slide 10 测试与效果

不要保留“12 passed”。最终以重新运行截图为准：

```powershell
cd E:\jobguard\jobguard\backend
.\.venv\Scripts\python.exe -m pytest
```

前端以重新构建截图为准：

```powershell
cd E:\jobguard\jobguard\frontend
npm run build
```

### Slide 12 总结与展望

保留“不足与限制”，但表达要更合规：

- 免费公开数据源有限。
- 访问控制网站不能无人值守自动化。
- 企业核验是辅助决策，不是最终背调结论。
- 后续可接入合规企业数据 API、后台队列、线上部署和用户测试。

## 4. 海报需要改的点

当前海报视觉效果可以保留，内容建议微调：

- “多智能体工作流”改为“LangGraph Agent 工作流”，避免老师追问为什么不是多个独立 Agent 协同。
- “企业核验”改为“企业证据核验/人工复核清单”，更符合当前合规边界。
- 技术栈增加 “MCP / OCR / AgentOps”。
- “RAG 检索相关项目”如果现场不能稳定演示，应改为“基于画像和目标岗位生成定向简历”。

## 5. 视频脚本需要改的点

视频里不要口播这些高风险句子：

- “检索企业社保人数和劳动争议记录”
- “抓取网络口碑”
- “61 个岗位全量背调成功”
- “所有判断都有信息输入支撑”

建议改为：

- “系统会展示已接入或已入库的可核验来源；对受访问控制的网站，会明确标为需要人工核验。”
- “没有来源时不会生成具体社保人数、劳动仲裁数量或口碑评分。”
- “这套机制的重点是防止大模型把未核验事实说成确定事实。”

## 6. 推荐最终叙事

JobGuard 不是一个追求“全自动背调”的系统，而是一个更适合作为课程项目和简历项目展示的“证据门禁式求职 Agent”：

1. 解决真实求职问题。
2. 有前端、后端、数据库和数据导入。
3. 有 LangGraph 工作流和 MCP 工具。
4. 有用户画像、岗位推荐、企业核验和定向简历业务闭环。
5. 有可观测性和测试体系。
6. 对访问受限和隐私风险保留人工确认。
