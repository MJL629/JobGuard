## 1. 项目简介

JobGuard 是一个面向计算机方向求职者的 AI 求职辅助系统。系统围绕“求职画像构建、岗位推荐、岗位风险分析、企业核验、定向简历生成”形成完整业务闭环，目标是帮助学生和职场新人减少盲投、识别岗位风险，并把已有经历转化为更贴合目标岗位的简历表达。

项目不是单轮问答机器人，而是一个前端、后端、数据库、Agent 工作流和工具体系共同组成的求职 Agent 应用。

## 2. 真实业务痛点

当前求职场景中存在以下问题：

- 用户的求职画像通常不完整，只靠简历无法体现隐藏项目、比赛、科研、实习和真实偏好。
- 岗位描述存在信息不透明问题，例如加班强度、薪资结构、试用期、招聘真实性等需要二次核验。
- 简历投递往往缺少针对性，用户不知道如何根据目标岗位重写项目经历和技能表达。
- 企业风险信息分散在工商、公开信用、裁判文书、招聘来源等多个渠道，普通用户难以系统核验。
- 大模型容易在无来源时虚构企业社保人数、劳动仲裁数量、公司口碑等敏感事实。

JobGuard 的产品定位是：让 AI 先理解用户，再结合可追溯岗位和企业来源，给出可解释、可复核、可继续修改的求职建议。

## 3. 项目目标与验收标准

| 目标 | 验收标准 |
|---|---|
| 构建求职画像 | 用户可通过对话和简历上传补充城市、薪资、岗位方向、技能、项目、比赛、实习、加班偏好等信息，并持久化到 MySQL |
| 推荐岗位 | 岗位列表来自数据库，推荐结果根据用户画像计算，不再所有岗位同分或同理由 |
| 岗位风险分析 | 用户可粘贴岗位描述、输入岗位链接或上传岗位截图，系统提取公司和岗位信息并生成风险分析 |
| 企业核验 | 报告区分已核验、未核验、受访问控制、无统一开放接口，不允许模型虚构外部事实 |
| 定向简历生成 | 用户选择目标岗位和模板后，系统基于已保存画像、简历和岗位要求生成 DOCX/PDF/Markdown |
| Agent 可观测 | Agent 运行、工具调用、失败步骤、耗时和评估信息可在 `/agent-ops` 查看 |

## 6. 产品业务链路

1. 用户登录系统。
2. 系统通过对话主动引导用户构建求职画像。
3. 用户上传简历，系统保存原文件并解析学历、技能、项目、经历等信息。
4. 用户补充简历中没有写出的项目、比赛、实习、科研、证书和偏好。
5. 系统根据画像和岗位库推荐岗位。
6. 用户进入岗位分析页，查看 JD 原文风险、官方招聘来源、企业核验结果和投递建议。
7. 用户选择目标岗位和简历模板，生成定向简历。
8. 系统在 Agent 观测页展示调用链、工具成功率、失败原因和耗时。

## 7. 已实现功能

### 7.1 登录与权限

系统已实现登录接口、前端登录页和认证依赖。后端使用认证上下文识别当前用户，避免继续依赖固定 `user_id=1` 造成用户数据串号。

### 7.2 深度对话画像

系统支持通过多轮对话收集求职方向、城市、薪资、技能、项目、比赛、实习、科研、证书、工作强度偏好等信息。对于“可以接受偶尔正常加班，但不接受长期高强度加班”这类细粒度表达，系统会先复述确认，再保存，避免把用户原意压缩成“完全不接受加班”。

### 7.3 简历上传与解析

系统支持多份简历保存，可保存原始文件、解析状态、SHA-256、解析器信息、OCR 状态和结构化结果。支持 PDF、DOCX、TXT、Markdown、图片等格式。解析失败时保留文件并标记“需要复核”，不把失败误判为文件丢失。

### 7.4 岗位库与推荐

岗位数据来自数据库，包含种子岗位和北京市公共数据开放平台导入的招聘岗位。系统会过滤过期岗位、标记来源，并根据用户画像计算匹配度、证据覆盖率、硬条件冲突和需要确认项。

### 7.5 岗位截图与链接分析

用户可以上传岗位截图，系统通过 OCR 或多模态模型提取公司、岗位和 JD 信息。对于岗位 URL，系统包含安全抓取边界：限制协议、跳转、响应大小、内网地址、内容类型和超时，不会让模型凭空补写未抓取到的 JD。

### 7.6 企业风险分析与证据门禁

岗位分析报告区分 JD 原文风险、官方招聘来源、企业证据、公开搜索结果、受访问控制来源和未核验字段。对于国家企业信用信息公示系统、中国裁判文书网等存在验证码或登录限制的网站，系统不会绕过验证，也不会把人工入口冒充成自动核验。

### 7.7 定向简历生成

系统支持用户选择目标岗位和简历模板，基于已保存画像、简历、补充经历和岗位要求生成定向简历。生成过程包含事实保护：学校、技能、项目和量化数字必须能回溯到用户画像、简历或补充经历。

### 7.8 MCP 与 Agent 工具

系统提供 MCP stdio 服务，暴露企业证据查询、岗位库检索、岗位要求分析、学习资源推荐、人工核验计划和工具状态等工具。应用内 Agent 和 MCP 复用同一套真实实现，不是临时写死的展示数据。

### 7.9 可观测性

系统包含 `/agent-ops` 页面，展示 Agent 运行记录、工具调用记录、成功率、失败步骤、耗时和评估信息。后端持久化 `agent_runs`、`tool_call_traces`、`agent_evaluations` 等运行数据。

- 企业核验来源不足

## 9. Prompt 迭代记录示例

| 阶段 | 原始问题 | Prompt/需求调整 | 结果 |
|---|---|---|---|
| 画像语义 | 用户表达“不接受高强度加班”被泛化 | 要求模型保留限定条件，先复述再确认 | 加班频率和强度限制分开保存 |
| 岗位推荐 | 所有岗位显示相同匹配分 | 要求区分 fit_score、coverage、hard_constraint_status | 低证据岗位显示“暂不评分”，有证据岗位显示差异化理由 |

| SSE 流式 | 前端出现重连 5 次 | 要求统一 SSE 事件结构和失败提示 | 降低重复、丢失、截断风险 |

## 10. 调试与问题解决记录

### 10.1 SSE 重连五次

现象：聊天页面在模型思考时显示“正在重新连接 5/5”。  
原因：前端 SSE 解析和后端事件边界不稳定时，容易被误判为连接失败。  
处理：梳理 SSE 协议测试，增加结构化事件和失败提示，避免内容重复、截断或空转。

### 10.2 简历上传解析失败

现象：用户在求职画像页上传简历后提示解析失败。  
原因：早期仅支持有限格式，且解析失败时没有把“文件已保存”和“结构化解析失败”区分开。  
处理：增加多格式解析、OCR、原文件保存、解析状态和中文失败原因。

### 10.3 岗位推荐同分

现象：多个岗位推荐理由类似，匹配分数相同。  
原因：用户画像稀疏时，缺失字段被固定中性分填充，造成虚假精确度。  
处理：拆分匹配分、证据覆盖率、硬条件冲突和需要确认项，证据不足时不显示误导性百分比。

### 10.4 企业核验受限

现象：工商、裁判文书、社保等字段大量显示“未接入”。  
原因：部分官方平台存在验证码、登录或实名认证限制，不能稳定、合规地无人值守抓取。  
处理：系统保留人工核验入口，并明确标注“受访问控制”或“未核验”，避免模型虚构。

### 10.5 定向简历生成超时

现象：前端 30 秒超时，用户看不到生成结果。  
原因：定向简历包含岗位分析、项目筛选、事实核查、DOCX/PDF 导出，耗时超过普通 API。  
处理：放宽超时边界，增加生成历史和下载入口，后续计划迁移到后台队列。

## 12. 技术创新点

### 12.1 证据门禁机制

系统把“模型生成”和“事实核验”分开：模型可以解释 JD 原文，但不能凭空生成社保人数、仲裁数量、工商风险和公司口碑。没有来源时必须标记未核验。

### 12.2 求职画像与简历联动

用户画像不只来自简历，还来自多轮对话。系统会引导用户补充简历里没有写出的项目、比赛、实习、科研和证书，并把这些信息用于岗位推荐和定向简历。

### 12.3 LangGraph 确定性主链

系统使用 LangGraph 组织意图分类、任务规划和证据门禁，把工具选择和业务边界纳入可观测流程。

### 12.4 MCP 工具接入

项目将内部工具通过 MCP stdio 暴露，使岗位检索、企业证据查询、学习资源推荐和工具状态查询具备标准化工具接口。

### 12.5 Agent 可观测性

系统记录 Agent 运行、工具调用、失败步骤、耗时和评估结果，让项目不只依赖“感觉效果不错”，而是可以定位失败和评估质量。

## 13. 人机协同与安全边界

系统保留人工确认环节：

- 高影响画像字段需要用户确认后保存。
- 定向简历不能编造用户没有提供的学校、项目或数字。
- 涉及登录、验证码、实名认证的网站不做无人值守自动化。
- 对外投递、账号操作、资金操作和隐私数据处理不自动执行。
- `.env`、API Key、Cookie、验证码和 userKey 不进入提交材料。

- 定向简历生成仍可能耗时较长，适合迁移到后台队列。
- Agent 质量评估还需要更完整的离线金标数据集。
- README 仍需更新，避免与当前实际完成度不一致。
